1.0

Executive Summary

1.1Key Takeaways

This deep review covered the Acme Shop API and its React storefront on branch main, ahead of the 2.5 release that opens the shop to guest checkout.

Two problems need fixing before release. The API decodes admin tokens without checking their signature, so anyone can forge an admin session (4.1.1). The payment webhook trusts any caller, so an attacker can mark an unpaid order as paid (4.1.2).

Database access is parameterised throughout, passwords are hashed with Argon2id, session cookies are HttpOnly and SameSite=Lax, and file uploads are type-checked and stored outside the web root.

A07:2025, API2:2023, CWE-347, CWE-287, ASVS V9.1

Description

requireAdmin reads the bearer token with jwt.decode, which parses the token without checking its signature, and then trusts the role claim. Every route under /api/admin relies on this middleware.

Attack scenario
  1. The attacker, with no account, builds a token with the payload {"sub":"1","role":"admin"} and any signature.
  2. They send GET /api/admin/customers with that token in the Authorization header.
  3. The middleware accepts the token and the API returns every customer record.
Impact

Full admin access without credentials: read and change every customer, order and product, and issue refunds.

Recommendation

Replace jwt.decode with jwt.verify(token, config.jwtSecret, { algorithms: ['HS256'] }), as requireUser already does in the same file. Add a test that a token signed with another key gets 401.

Proof of concept acme-shop/api/src/middleware/auth.js 
function requireAdmin(req, res, next) {
  const token = (req.headers.authorization || '').replace('Bearer ', '');
  const claims = jwt.decode(token);
  if (!claims || claims.role !== 'admin') {
    return res.status(403).json({ error: 'forbidden' });
  }
  req.user = claims;
  next();
}

A08:2025, API6:2023, CWE-345, ASVS V2.3

Description

The payment webhook marks an order as paid from the orderId and status in the request body. It never checks the provider's Payment-Signature header, and the route is public so the provider can reach it.

Attack scenario
  1. The attacker places an order and stops at the payment page.
  2. They send POST /api/webhooks/payment with {"orderId":"<their order>","status":"succeeded"}.
  3. The order moves to paid and is released for shipping.
Impact

Goods shipped without payment, for any order the attacker can create.

Recommendation

Verify the Payment-Signature header with the provider SDK's constructEvent and the webhook secret before reading the body, and re-fetch the payment from the provider by id before changing the order. Add a test that an unsigned callback gets 400 and leaves the order unchanged.

Proof of concept acme-shop/api/src/routes/webhooks.js 
router.post('/payment', express.json(), async (req, res) => {
  const { orderId, status } = req.body;
  if (status === 'succeeded') {
    await orders.markPaid(orderId);
  }
  res.sendStatus(200);
});

A01:2025, API1:2023, CWE-639, ASVS V8.2

Description

GET /api/orders/:id loads the order by id only. The query has no customer_id filter and the handler does not compare the owner with req.user.id. Order ids are sequential.

Attack scenario
  1. The attacker signs up as an ordinary customer.
  2. They request GET /api/orders/1, /2, /3 and so on.
  3. Each response returns another customer's name, delivery address, phone number and items.
Impact

Any customer can read every other customer's order history and personal data.

Recommendation

Load the order with orders.findForCustomer(id, req.user.id) (the helper the order list already uses) and return 404 when it finds nothing. Add a test that customer B gets 404 for customer A's order.

Proof of concept acme-shop/api/src/routes/orders.js 
router.get('/:id', requireUser, async (req, res) => {
  const order = await orders.findById(req.params.id);
  if (!order) {
    return res.sendStatus(404);
  }
  res.json(order);
});

Description

The global error handler sends err.stack to the client in every environment. A malformed request body is enough to trigger it.

A06:2025, API6:2023, CWE-362, ASVS V2.3

Description
Needs confirmation

redeem reads used_at, checks it is empty and then updates it in a separate statement. Two requests sent together can both pass the check. Whether this works depends on the database isolation level, which is not in the repository.

Attack scenario
  1. The attacker holds one single-use coupon and two carts.
  2. They send both checkout requests with the coupon at the same moment.
  3. Both orders get the discount.
Impact

A single-use discount applied more than once. The loss per coupon is small, but the same pattern is easy to script.

Recommendation

Redeem with one conditional update, UPDATE coupons SET used_at = now() WHERE code = $1 AND used_at IS NULL RETURNING id, and reject the checkout when no row comes back. Add a test that fires two redemptions in parallel.

Proof of concept acme-shop/api/src/services/coupons.js 
async function redeem(code, orderId) {
  const coupon = await db.one('SELECT * FROM coupons WHERE code = $1', [code]);
  if (coupon.used_at) {
    throw new CouponUsedError();
  }
  await db.none('UPDATE coupons SET used_at = now(), order_id = $2 WHERE id = $1', [coupon.id, orderId]);
}

A05:2025, CWE-79, ASVS V3.2, WSTG-CLNT-03

Description

Review text is rendered with dangerouslySetInnerHTML so that line breaks show. The API stores review text as submitted, so any customer can store markup that runs in other shoppers' browsers.

Attack scenario
  1. The attacker, signed in as a customer, posts a review containing <img src=x onerror=...>.
  2. Another shopper opens the product page.
  3. The script runs in the shopper's session and can act as them on the storefront.
Impact

Actions in a victim's session, such as changing the delivery address of an open order. The session cookie itself is HttpOnly.

Recommendation

Render the text as a React child and use CSS white-space: pre-line for line breaks. Add a test that a review containing <img> renders as text.

function ReviewBody({ review }) {

      className="review-body"

    />
  );
}

A07:2025, CWE-922, ASVS V3.3, RFC 10017

Description

The storefront stores the long-lived refresh token in localStorage, where any script on the page can read it. Combined with 4.2.1, an attacker could take the token and keep access after the victim leaves the page.

Attack scenario
  1. The attacker gets script running on the storefront (for example through 4.2.1).
  2. The script reads localStorage.refreshToken and sends it to the attacker.
  3. The attacker uses the token to get new access tokens for the victim's account.
Impact

Long-lived access to one customer's account. It needs a separate script-injection flaw first.

Recommendation

Have the API set the refresh token as an HttpOnly, Secure, SameSite=Strict cookie scoped to /api/auth/refresh, and keep only the short-lived access token in memory.

Proof of concept acme-shop/web/src/api/client.js 
export function saveTokens({ accessToken, refreshToken }) {
  memory.accessToken = accessToken;
  localStorage.setItem('refreshToken', refreshToken);
}

6.1Assessment Methodology

This review was performed with the appsec-review skill, commit sample.

  • Code enumeration. inventory.py listed 41 routes, 1 webhook, 23 screens and 57 sinks across api/ and web/; the coverage ledger tracked each one to a result.
  • Dependency and secret checks. npm audit and gitleaks were run; neither reported an issue in scope. osv-scanner and semgrep were not installed.
  • Manual source analysis. Followed each entry point (routes and handlers, screens and client flows) through its middleware, filters and guards to its sinks, with a STRIDE pass on every trust boundary, against the checklist in section 3.0 and the stack checks for Node.js 22 with Express 5 and PostgreSQL · React 19 single-page app.
  • Verification. Every candidate was checked by a fresh verifier agent that did not see the finder's reasoning; one rejection was reviewed and overruled (4.2.2).
  • Run. deep mode, 38m 12s, 1,284,500 tokens (main session and subagents).
